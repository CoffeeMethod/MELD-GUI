Overview

The released MELD checkpoint ships a short scorer that answers one question: what is P(AI) for this document? That number on its own is hard to act on. This app keeps that computation bit-for-bit identical and adds the context needed to actually read it.

Calibrated decisions

Scores are compared against the false-positive-rate thresholds shipped in the checkpoint, per document genre — not against an arbitrary 0.5.

Evidence, not verdicts

The document score pools the most machine-like 25% of tokens, so per-token margins already exist. They are mapped back to the text as a heatmap.

Any length

Documents past 2,048 tokens are scored in overlapping windows and pooled, with each window reported separately.

Scriptable

The interface is a client of the app's own REST API. Anything you can click, you can automate.

Installation

Python 3.10 or newer. A CUDA GPU is optional — the model runs on CPU too, just slower.

git clone https://github.com/CoffeeMethod/meld-gui.git
cd meld-gui

python -m venv .venv
.venv\Scripts\activate          # Windows
source .venv/bin/activate       # macOS / Linux

pip install -r requirements.txt
GPU users: the default torch wheel is CPU-only. For CUDA, install it explicitly first — pip install torch --index-url https://download.pytorch.org/whl/cu124 — then run the requirements install.

First run

python -m meld_gui

This opens http://127.0.0.1:8000. The checkpoint is not bundled: on first use go to Model → Download & load to fetch it (~1.6 GB, cached in your HuggingFace folder afterwards, so this happens once).

Once the sidebar pill reads Model ready, paste a document into the editor and press Ctrl + Enter.

Verifying the install

pytest -m "not model"    # 36 logic tests, no checkpoint needed
pytest                   # all 53, including live-model integration

Reading a result

A flag is not proof. At a 1% false-positive rate, scanning 500 genuinely human essays still produces about five wrong flags. Use this to prioritise a human review — never as the sole basis for a decision about a person.

Raw score vs probability

MELD's decision happens in raw-score space. The percentage on the gauge is simply sigmoid(raw score) — a squashed view of the same number, not a calibrated "chance this is AI". Two documents at 99.2% and 99.6% may be far apart in raw score; two at 30% and 35% may be nearly identical.

Read the margin instead: how far the raw score sits above or below your chosen cut-off. That is the number the verdict is built on.

Verdict bands

The flag itself is always score > threshold. The four bands are a presentation layer on top of the margin:

BandMargin vs cut-offReading
Strong AI signal≥ +2.0Well past the cut-off.
Likely AI-generated0 to +2.0Flagged, but near the boundary.
Inconclusive−1.5 to 0Below the cut-off, but not comfortably.
Likely human-written< −1.5Inside the human range.

The 100-word floor

Short text scores high regardless of who wrote it. Below 100 words the result is noise, and the app says so explicitly rather than showing a confident-looking number. The length bar under the editor tracks this.

Thresholds & false-positive rate

The checkpoint was calibrated on 12,461 human documents. It ships, for each genre, the raw score below which 99% / 95% / 90% of that genuine human writing fell. Choosing 1% FPR means roughly one human document in a hundred of that genre would be wrongly flagged.

These vary a great deal, which is why setting Document type matters more than most users expect:

Document type1% FPR5% FPR10% FPRCalibration n
General / mixed+1.92−0.47−1.2612,461
Academic writing+1.21−1.15−1.441,654

A raw score of +1.6 is flagged as academic writing and cleared as general prose. Same document, same model, different question being asked.

Which FPR should I pick? 1% when a false accusation is costly — graded work, hiring, anything involving a named person. 5–10% when you are triaging a large pile and a human will look at everything flagged anyway.

Sentence heatmap

The document score is the mean of the most machine-like ρ = 25% of tokens. That means per-token margins are computed as a matter of course; the app maps them back to character offsets and colours the text.

Each sentence gets the same top-25% pooling applied within itself, so the colour answers "how machine-like is the most machine-like quarter of this sentence". Toggle Token-level detail for per-token shading instead.

Sentence colours are diagnostic, not decisions. The thresholds were calibrated on whole documents of 100+ words, so a single red sentence means far less than a consistently red document.

This is the reason a mostly-human document with a few generated paragraphs can still score high overall — and the heatmap is how you find those paragraphs.

Long documents

MELD reads 2,048 tokens at a time. Longer documents are handled like this:

  1. Window. The token stream is cut into overlapping windows (2,046 content tokens, 128 overlap by default).
  2. Score. Windows are batched through the model.
  3. Stitch. Where two windows cover the same token, the copy that sat furthest from a window edge wins — it was scored with the most context on both sides.
  4. Pool. The released top-25% rule is then applied across the whole document, not per window.

The Windows tab shows each window's own score, so you can see whether a long document is uniformly machine-like or only in places.

Attribution

The checkpoint carries 11 model-family prototypes and 9 edit-operation prototypes. The Attribution tab reads the softmax over those prototypes for the tokens that actually drove the score.

gptllamamistral mptcoheregoogle anthropicqwenlegacy_open essay_aiunknown_ai
polishparaphraseacademic humanizeroundtripsummarize expandgenerate_from_context generate_from_abstract
Indicative only. These prototypes ship in the checkpoint, but the model card publishes no accuracy figures for them. Read the output as a stylistic lean, never as identification of a specific model or a specific editing step.

The five views

Analyze
One document. Gauge, calibrated score scale, sentence heatmap, sortable sentence table, attribution, per-window breakdown, statistics, raw JSON. Exports to JSON, CSV and print.
Batch
Drop many files at once. Results stream in as each finishes, with a running flagged count and CSV export.
Compare
Two documents under identical settings, with the raw-score delta spelled out. Useful for before/after edits, or scoring a known-human control alongside the document you actually care about.
History
Every run is stored in local SQLite. Searchable, filterable to flagged only, re-openable, CSV exportable.
Model
Download progress, device selection, and a live read of the checkpoint's configuration and calibration table.

Scoring a document

import requests

BASE = "http://127.0.0.1:8000"
requests.post(f"{BASE}/api/model/load")          # once per server start

r = requests.post(f"{BASE}/api/analyze", json={
    "text": open("essay.txt", encoding="utf-8").read(),
    "stratum": "academic",       # match the genre being checked
    "fpr": "fpr_0.01",           # 1% false-positive rate
}).json()

d = r["decision"]
print(f"{d['probability']:.1%}  raw={d['score']:+.2f}  "
      f"cut-off={d['threshold']:+.2f}  flagged={d['flagged']}")

for s in sorted(r["sentences"], key=lambda s: -s["score"])[:3]:
    print(f"  {s['score']:+.2f}  {s['text'][:70]}")

Response shape

{
  "decision":    { "score", "probability", "threshold", "margin",
                   "flagged", "verdict", "verdict_label", "stratum", "fpr" },
  "statistics":  { "words", "sentences", "paragraphs", "type_token_ratio", ... },
  "tokens":      { "count", "windows", "rho", "pooled_tokens", "max_length" },
  "timing":      { "seconds", "tokens_per_second", "device" },
  "warnings":    [ { "level", "message" } ],
  "attribution": { "families": [...], "operations": [...], "note" },
  "sentences":   [ { "index", "start", "end", "text", "score",
                     "probability", "flagged", ... } ],
  "chunks":      [ { "index", "token_start", "token_end", "score", ... } ],
  "token_detail":{ "offsets": [[start, end], ...], "scores": [...] }
}
Offsets are exact. Every start/end pair indexes into the string you submitted, so text[s["start"]:s["end"]] reconstructs the sentence verbatim. A test asserts this.

Batch scanning a folder

import time, pathlib, requests

BASE = "http://127.0.0.1:8000"
docs = [{"name": p.name, "text": p.read_text(encoding="utf-8")}
        for p in pathlib.Path("essays").glob("*.txt")]

job = requests.post(f"{BASE}/api/batch",
                    json={"documents": docs, "stratum": "academic"}).json()

while True:
    status = requests.get(f"{BASE}/api/batch/{job['id']}").json()
    print(f"{status['completed']}/{status['total']}", end="\r")
    if status["status"] != "running":
        break
    time.sleep(0.5)

for item in status["items"]:
    if item.get("flagged"):
        print(f"FLAG  {item['probability']:.1%}  {item['name']}")

Decisions worth knowing

The scoring maths is never re-derived
core/model.py reproduces the model card's score() exactly, and a test asserts parity to 1e-4. Everything else reads the intermediate tensors that computation already produces. If the upstream checkpoint changes, that is the one file to update.
No frontend build step
Four plain .js files and one .css. Deliberate: it keeps the app runnable years from now without a dead toolchain.
History is boring on purpose
One SQLite table, no ORM, no migration framework. It stores the full result JSON alongside indexed summary columns, so re-opening a past run needs no re-scoring.

The model-marked tests skip themselves automatically when the checkpoint is not present, so a clean checkout stays testable. Limitations

  • English only. The model was trained and calibrated on English.
  • Short text is noise. Below 100 words, scores run high regardless of author.
  • Non-native writing. Most detectors score non-native English higher; MELD's calibration set may not match your population. This is the single most common source of unfair flags.
  • Formulaic prose. Documentation, boilerplate and legal text are naturally low-variance and read as machine-like.
  • Mixed authorship. AI-assisted human writing lands in the inconclusive band — which is the honest answer, not a failure.
  • No detector is a lie detector. There is no threshold at which a score becomes evidence about a person.

FAQ

Does any of my text leave my machine?

No. The only network request the app makes is downloading the checkpoint from HuggingFace on first run. Analysis is local, and history is a SQLite file in data/.

Why is the probability 99% when the raw score barely cleared the cut-off?

Because probability is sigmoid(raw score), which saturates fast. A raw score of +5 and +9 both read as "99-point-something percent". Use the margin column instead — it is the number that carries information near the boundary.

Can I run it without a GPU?

Yes. Pass --device cpu or just let it auto-detect. Expect roughly an order of magnitude slower, which for a single document is still a couple of seconds.

Where is the model stored?

Your HuggingFace cache — typically ~/.cache/huggingface/hub — so it is shared with any other tool using the same checkpoint. Point MELD_MODEL_DIR at a folder to override.

My document is 40,000 words. Will it work?

Yes, in overlapping windows. The default character cap is 400,000; raise MELD_MAX_CHARS if you need more. Check the Windows tab — a long document is often not uniform.

A student says the flag is wrong. What now?

Take that seriously. At 1% FPR you should expect false flags at a rate of about one per hundred human documents, and higher for non-native writers. The heatmap and per-window scores exist to support a conversation, not to close one. A detector score is not evidence on its own.

Can I change the verdict thresholds?

The calibrated cut-offs come from the checkpoint and should not be invented. The presentational bands are yours to adjust in core/thresholds.py → _BANDS.
